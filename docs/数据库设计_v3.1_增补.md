# 数据库设计 v3.1 增补（配套接口 v3.1 增补）

> 本文件是《完整数据库设计_全模块_v3.md》的**增补篇**，不覆盖 v3.0 原文。
> 只列出「因为接口 v3.1 增补而必须改」的表结构，以及核对后**确认不需要改**的部分。
> 表命名、字段命名、字符集（utf8mb4 / utf8mb4_unicode_ci）、逻辑删除（`deleted`）、
> 审计字段（`create_time` / `update_time`）全部沿用 v3.0 风格。

---

## 一、结论速览

| # | 涉及表 | 是否必须改 | 原因 |
|---|---|---|---|
| 1 | `user`.`username` | **必须** | `NOT NULL UNIQUE`，但新注册流程不再传用户名 → 插入直接失败 |
| 2 | `user`.`email` | **必须** | 缺唯一索引 → 同一邮箱可注册多账号，1009 错误码无法实现 |
| 3 | `user`.`phone` 长度 | **须约定** | 只有 `VARCHAR(20)`，邮箱地址塞进去会截断/报错，必须按通道分列落库 |
| 4 | `file_record` | **必须新增** | 6 处图片落库都需要一个能按 `fileId` 删除/回收的登记表；v3.0 无此表 |
| 5 | `article` / `course` / `download_record` | 建议 | 列表「最热」排序与下载记录筛选缺组合索引，会走全表扫 |
| 6 | `verification_code` | 不用改 | 已有 `target_type`（1手机号/2邮箱）与 `scene`，天然支持邮件验证码 |
| 7 | `sign_record` | 不用改 | 已有 `photo_url`，拍照签到可直接落库 |
| 8 | `note` / `todo` | 不用改 | 与接口 10.x/11.x 完全一致 |
| 9 | `resource`（下载资源表） | **v3.0 本来就缺失** | 接口 12.1 要 `resourceId`，`download_record.resource_type/resource_id` 也要指向它，但库设计里没有这张表 |

## 二、必改一：`user` 表 —— 不改正则注册直接失败

### 2.1 问题

v3.0 的 `user` 表：

```sql
`username`  VARCHAR(50)  NOT NULL  COMMENT '登录账号',
...
UNIQUE KEY `uk_username` (`username`),
```

而接口 v3.1 增补后的 2.2 注册请求体只有：

```
account / accountType / password / code / nickname(选填) / email(选填)
```

**没有 `username`**。`username` 是 `NOT NULL` 且无默认值，插入必然失败
（`Field 'username' doesn't have a default value`）。

同时 `email` 在 v3.0 里**没有唯一索引**，邮箱注册会失去唯一性约束 —— 同一个人可以用
同一个邮箱注册多个账号，且 1009「邮箱已被注册」这个新错误码无法可靠实现。

### 2.2 还有一个坑：`phone` 只有 VARCHAR(20)，装不下邮箱

v3.0 的列定义：

```sql
`phone`  VARCHAR(20)  DEFAULT NULL  COMMENT '手机号',
`email`  VARCHAR(100) DEFAULT NULL  COMMENT '邮箱',
```

`VARCHAR(20)` 是**按手机号长度定的**（11 位国内手机号 + 区号足够）。
但邮箱注册时，邮箱地址**只能进 `email` 列，绝不能塞进 `phone` 列**：

| 邮箱 | 长度 | 能否放进 `phone VARCHAR(20)` |
|---|---|---|
| `a@b.cn` | 6 | 可以 |
| `zhangsan@qq.com` | 15 | 可以 |
| `zhangsan@example.com` | 20 | 刚好卡住 |
| `zhangsan2026@university.edu.cn` | 31 | **超长，插入报错或静默截断** |

MySQL 非严格模式下会**静默截断到 20 字符**，结果是「注册成功但邮箱存成了
`zhangsan2026@unive`」—— 之后用真实邮箱登录永远失败，而且用户看不出问题所在。
严格模式（`STRICT_TRANS_TABLES`，MySQL 5.7+ 默认开启）则直接报
`Data too long for column 'phone'`。

**约定（写入接口文档 v3.1 增补 2.2 已明确，此处再强调一次）**：

```
accountType = 1（手机号）→ 写 `phone` 列，`email` 写 NULL
accountType = 2（邮箱）  → 写 `email` 列，`phone` 写 NULL   ← 关键
```

如果后端实现时图省事，把 `account` 一律写进 `phone`，个人邮箱就会大量注册失败。

> 客户端侧已经不会再触发这个问题：早期版本曾用 `phone = email` 的变通写法，
> 现在改为发送 `account` + `accountType` 两个字段，由服务端按通道分列落库。

### 2.3 改法

选 A 或 B 其一（推荐 A，改动最小且向后兼容）。

#### 方案 A（推荐）：`username` 可空 + 自动生成，`email` 加唯一索引

```sql
ALTER TABLE `user`
  MODIFY COLUMN `username` VARCHAR(50) DEFAULT NULL COMMENT '登录账号（可空：手机号/邮箱注册时由服务端生成 user_{user_id}）',
  ADD UNIQUE KEY `uk_email` (`email`);
```

配套约定（**后端实现必须遵守，否则唯一索引会误伤**）：

1. 手机号或邮箱注册时，`username` 留 `NULL`，或由服务端生成 `user_{user_id}` 后回填。
2. `phone` / `email` 中**没用到的那一列必须写 `NULL`，不能写空串 `''`**。
   MySQL 的 UNIQUE 索引允许多个 `NULL`，但**只允许一个 `''`**——
   第二个不写邮箱的用户就会撞 `uk_email` 报「邮箱已注册」。
3. 邮箱只能写 `email` 列（见 2.2），不要写 `phone`。
4. 2.3 登录时 `username` 字段按「`username` / `phone` / `email` 三选一命中」查询。

> 方案 A 的风险：`username` 允许 `NULL` 后，老代码里若把 `username` 当必填使用会读到 `NULL`。
> 建议服务端在注册成功后**一定回填** `user_{user_id}`，让 `username` 实际上永不为 `NULL`，
> 只是取消了「由用户提供」这个语义。

#### 方案 B：保留 `NOT NULL`，服务端强制生成

```sql
ALTER TABLE `user`
  MODIFY COLUMN `username` VARCHAR(50) NOT NULL COMMENT '登录账号（服务端生成，用户不可自定义）',
  ADD UNIQUE KEY `uk_email` (`email`);
```

不改可空性，注册时服务端生成 `user_{timestamp}` 或 `user_{随机串}` 填入。
代价：**用户注册时填的用户名会丢失**（UI 稿上有这一项，需产品确认是否接受）。

**无论 A 还是 B，`uk_email` 都必须加**，否则 1009 无法实现。

### 2.3 不需要改的部分

`phone VARCHAR(20) DEFAULT NULL` + `uk_phone` 已经满足手机号注册，
只要遵守「不用就写 NULL」即可。

## 三、必改二：新增 `file_record` 表

### 3.1 为什么非加不可

v3.0 的库设计里**没有任何文件表**，但接口 v3.1 增补 15.1 定义了：

- 响应里返回 `fileId`
- 15.2 提供 `DELETE /api/v1/files/{fileId}`

如果没有登记表，`fileId` 无处持久化，删除接口无法实现，也无法做存储回收。
同时这张表还能承载「上传去重」和「运营统计」两个附带价值。

### 3.2 建表语句

```sql
CREATE TABLE `file_record` (
  `id`             BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `file_id`        VARCHAR(64)  NOT NULL                COMMENT '文件唯一标识（服务端生成；建议 sha256(用户ID+时间戳+随机数) 取前32位）',
  `original_name`  VARCHAR(255) DEFAULT NULL            COMMENT '上传时的原始文件名',
  `file_name`      VARCHAR(255) NOT NULL                COMMENT '服务端生成的文件名（落盘/对象存储用）',
  `file_url`       VARCHAR(512) NOT NULL                COMMENT '公网访问URL（建议存相对路径，网关/客户端拼域名，见3.4）',
  `storage_key`    VARCHAR(512) DEFAULT NULL            COMMENT '对象存储key（OSS/COS key 或本地相对路径），删除物理文件时用',
  `storage_type`   TINYINT      NOT NULL DEFAULT 1      COMMENT '存储类型：1-本地 2-阿里OSS 3-腾讯COS 4-七牛 5-其他',
  `mime_type`      VARCHAR(128) DEFAULT NULL            COMMENT '真实MIME（服务端按魔数识别，不信任客户端声明）',
  `file_ext`       VARCHAR(16)  DEFAULT NULL            COMMENT '扩展名（小写，不含点）',
  `file_size`      BIGINT       NOT NULL DEFAULT 0      COMMENT '文件大小（字节）',
  `width`          INT          DEFAULT 0               COMMENT '图片宽（px），非图片为0',
  `height`         INT          DEFAULT 0               COMMENT '图片高（px），非图片为0',
  `sha256`         CHAR(64)     DEFAULT NULL            COMMENT '文件内容哈希（去重用；相同哈希可直接复用已有URL）',
  `scene`          VARCHAR(32)  NOT NULL                COMMENT '业务场景：avatar/article_cover/article_image/note_image/checkin_photo/course_cover/resource',
  `biz_type`       TINYINT      DEFAULT NULL            COMMENT '关联业务类型：1-用户头像 2-文章 3-课程 4-签到 5-笔记 6-资源 7-无关联',
  `biz_id`         BIGINT       DEFAULT NULL            COMMENT '关联业务ID（如 article_id / sign_record.id）',
  `uploader_id`    BIGINT       DEFAULT NULL            COMMENT '上传人用户ID；管理员上传课程封面时为其 admin_id',
  `ref_count`      INT          NOT NULL DEFAULT 1      COMMENT '被引用次数（同一文件被多篇内容引用时累加，归零后可回收）',
  `status`         TINYINT      NOT NULL DEFAULT 1      COMMENT '状态：1-正常 0-已删除',
  `delete_time`    DATETIME     DEFAULT NULL            COMMENT '删除时间（15.2 调用时间）',
  `create_time`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_file_id` (`file_id`),
  KEY `idx_uploader_scene` (`uploader_id`, `scene`),
  KEY `idx_sha256_scene` (`sha256`, `scene`),
  KEY `idx_biz` (`biz_type`, `biz_id`),
  KEY `idx_status_time` (`status`, `create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='文件上传登记表（v3.1 新增）';
```

### 3.3 字段设计要点

| 设计 | 原因 |
|---|---|
| `uk_file_id` 唯一 | 15.2 的 `DELETE /files/{fileId}` 必须能唯一定位；也防止服务端 ID 生成碰撞 |
| `sha256` + `idx_sha256_scene` | 同一张图被多次上传时可直接复用已有 `file_url`，`ref_count + 1`。**注意同一 scene 才能复用**，跨 scene 复用会让「文章封面图 URL 出现在头像目录下」，不利于存储治理 |
| `ref_count` | 文章正文里同一张图可能被插入多次；头像被替换时旧文件可能仍被历史内容引用。**归零才允许物理删除**，避免删掉正在被引用的图 |
| `storage_key` 与 `file_url` 分开 | 换 CDN 域名时只需重写 `file_url`，不用改存储路径 |
| `biz_type` / `biz_id` 可空 | 上传时业务记录可能还没创建（先传图再发文章），此时留 `NULL`，业务成功后回填 |
| 不用 `deleted` 而用 `status` + `delete_time` | 文件的生命周期是「软删 → 定时任务物理删」，与业务表的逻辑删除语义不同，独立表达更清楚 |

### 3.4 `file_url` 长度的兼容风险（重要）

接口 v3.1 增补 15.1 里我写的是返回**完整公网 URL**。如果后端用带签名参数的临时 URL
（长 query string），长度很容易超过 255。所以本表 `file_url` 定为 `VARCHAR(512)`。

**但业务表里的 URL 列全都是 `VARCHAR(255)`**，这一点必须处理，见第四节。

## 四、必知：URL 列长度全线对照（`VARCHAR(255)` 够不够）

v3.0 里所有存文件 URL 的列：

| 表 | 列 | 当前长度 | 风险 |
|---|---|---|---|
| `user` | `avatar` | VARCHAR(255) | 低 |
| `article` | `cover_url` | VARCHAR(255) | 低 |
| `article` | `author_avatar` | VARCHAR(255) | 低 |
| `course` | `cover_url` | VARCHAR(255) | 低 |
| `content_category` | `icon_url` | VARCHAR(255) | 低 |
| `comment` | `user_avatar` | VARCHAR(255) | 低 |
| `sign_record` | `photo_url` | VARCHAR(255) | 低 |
| `note` | `source_cover` | VARCHAR(255) | 低 |
| `view_history` | `target_cover` | VARCHAR(255) | 低 |

**判断**：对典型 CDN 直链（`https://cdn.example.com/article_cover/2026/02/18/a1b2c3d4.jpg` ≈ 70 字符）**够用**。

**但两种情况会溢出**：

1. 对象存储返回带签名参数的临时 URL（`?Expires=...&Signature=...`），常见 300-600 字符；
2. 走图片处理参数（`?x-oss-process=image/resize,w_800/quality,q_85`）。

**建议**：接口 v3.1 增补 15.1 明确约定 **`file_url` 返回永久公网直链，不带签名参数**。
若后端确实只能用签名 URL，则以下列必须同步扩容：

```sql
-- 仅在「URL 带签名参数」时执行
ALTER TABLE `user`             MODIFY COLUMN `avatar`         VARCHAR(512) DEFAULT NULL COMMENT '头像URL';
ALTER TABLE `article`          MODIFY COLUMN `cover_url`      VARCHAR(512) DEFAULT NULL COMMENT '封面图URL',
                               MODIFY COLUMN `author_avatar`  VARCHAR(512) DEFAULT NULL COMMENT '作者头像（冗余）';
ALTER TABLE `course`           MODIFY COLUMN `cover_url`      VARCHAR(512) NOT NULL     COMMENT '封面图URL';
ALTER TABLE `content_category` MODIFY COLUMN `icon_url`       VARCHAR(512) DEFAULT NULL COMMENT '分类图标URL';
ALTER TABLE `comment`          MODIFY COLUMN `user_avatar`    VARCHAR(512) DEFAULT NULL COMMENT '用户头像（冗余）';
ALTER TABLE `sign_record`      MODIFY COLUMN `photo_url`      VARCHAR(512) DEFAULT ''   COMMENT '拍照上传图片URL';
ALTER TABLE `note`             MODIFY COLUMN `source_cover`   VARCHAR(512) DEFAULT NULL COMMENT '来源封面（冗余）';
ALTER TABLE `view_history`     MODIFY COLUMN `target_cover`   VARCHAR(512) DEFAULT NULL COMMENT '资源封面（冗余）';
```

> 客户端侧与此无关：Android 端只把服务端返回的 `url` 原样落库，不做长度截断。

## 五、建议改：列表查询索引

`ContentItemDto` 的列表来自三处查询，v3.0 的索引基本够用，但有两处会退化成全表扫。

### 5.1 `article` 按时间/热度排的最新列表

```sql
-- 现有：KEY idx_status_publish (status, publish_time)  —— 覆盖「最新」排序
-- 缺「最热」排序（按 view_count 倒序 + 已发布过滤）
ALTER TABLE `article` ADD KEY `idx_status_view` (`status`, `view_count`);
```

`course` 表已有 `idx_view_count`，但没和 `status` 组合：

```sql
ALTER TABLE `course` ADD KEY `idx_status_view` (`status`, `view_count`);
```

### 5.2 `view_history` 与 `note` 的列表

- `view_history` 已有 `idx_user_time (user_id, last_view_time)` ✅
- `note` 已有 `idx_user_create (user_id, create_time)` ✅
- `note` 的关键词搜索（10.1 的 `keyword`）走 `content` 的 `LIKE`，数据量大时慢。
  若笔记量级上来，建议加全文索引：

```sql
-- 可选：笔记量级 > 10万 再考虑
ALTER TABLE `note` ADD FULLTEXT KEY `ft_title_content` (`title`, `content`) WITH PARSER ngram;
```

### 5.3 `download_record` 按类型筛选

3.11 支持按 `resourceType` 筛选，v3.0 有 `idx_resource` 但那是 `(resource_type, resource_id)`，
按 `user_id + resource_type` 查会走不到索引：

```sql
ALTER TABLE `download_record` ADD KEY `idx_user_type_time` (`user_id`, `resource_type`, `create_time`);
```

## 六、不用改的部分（核对结论）

这几处我逐字段对过了，**v3.0 已经满足，不要重复加**：

### 6.1 `verification_code` —— 已天然支持邮件验证码

```sql
`target`      VARCHAR(100) NOT NULL  -- 手机号或邮箱
`target_type` TINYINT      NOT NULL DEFAULT 1  -- 1-手机号 2-邮箱
`scene`       VARCHAR(30)  NOT NULL  -- register/login/reset_password/change_phone/change_email
```

`target_type=2` 就是邮箱通道，`scene='register'` 复用。
**唯一要补的是业务逻辑**：发送时按 `target_type` 分流到短信网关或邮件服务，
并在 `send_status` / `fail_reason` 里记录邮件发送结果（如 SMTP 被拒）。
不需要 `ALTER TABLE`。

> 限流规则（60 秒一次）客户端已按 60 秒倒计时实现，服务端按 `idx_target_scene` 查最新一条即可。

### 6.2 `sign_record` —— 拍照签到直接可用

```sql
`photo_url` VARCHAR(255) DEFAULT ''  COMMENT '拍照上传图片URL（拍照签到）'
```

字段已存在，`uploadToScene=checkin_photo` 上传后的 `url` 直接写这里。
配合第四节，只在签名 URL 场景下需要扩容。

### 6.3 `note` / `todo` —— 与接口完全一致

- `note.source_type` / `source_id` 均 `NOT NULL`，正好对应接口 10.2 的必填约束。
  **注意**：我最初把「独立笔记」的 `source_id` 传 0，这个值在库层面合法（`NOT NULL` 不校验业务存在性），
  但业务上是脏数据。**建议后端对 `source_id=0` 做显式拒绝**，并告知客户端「笔记必须挂在具体内容下」，
  我会把新建入口从「笔记本页」挪到「文章详情页 / 播放页」。
- `todo.relate_type` / `relate_id` 可空，对应接口 11.2 的选填 ✅
- `todo.priority` 默认 2（中），与接口默认值一致 ✅

### 6.4 内容项 DTO 的字段来源

| `ContentItemDto` 字段 | 来源 |
|---|---|
| `id` | `article.article_id` 或 `course.course_id` |
| `type` | 查询时按来源表硬编码 1 / 2（**不是表里的列**，服务端拼装时写死） |
| `title` | `article.title` / `course.title` |
| `summary` | `article.summary` / `course.description`（取前 N 字截断） |
| `coverUrl` | `article.cover_url` / `course.cover_url` |
| `categoryId` / `categoryName` | `*.category_id` → `content_category.category_name`（需 JOIN） |
| `authorId` | `article.author_id` / `course.create_by`（课程无独立作者字段，用创建人） |
| `authorName` | `article.author_name`（冗余列，免 JOIN）/ `course.instructor_name` ✅ 两者都有冗余列 |
| `viewCount` / `likeCount` / `commentCount` | 各自表的计数字段 |
| `duration` / `score` | `course.duration` / `course.average_score`；文章固定 0 |
| `createTime` / `publishTime` | `*.create_time` / `*.publish_time` |

**结论：这一项不需要改表**，只需要服务端在拼装时把 `type` 写死并 JOIN `content_category` 取 `categoryName`。
`authorName` 两张表都有冗余列，**不必 JOIN `user`**。

### 6.5 `content_category` —— 分类页不用改

`type`（1文章 2课程）、`parent_id`、`sort`、`status`、`icon_url` 都在，多级树形靠 `parent_id` 自关联。
4.2 的「含子分类内容」靠 `parent_id IN (...)` 或加 `path` 列实现 —— 数据量小的话
`parent_id` 递归就够，**不建议现在加 `path`**。

## 七、发现一处 v3.0 的既有缺口：`resource` 表缺失

与 v3.1 增补无关，但核对时发现的，**顺手提醒**：

- 接口 12.1 是 `GET /api/v1/resources/download/{resourceId}`，需要一个 `resource` 表定义 `file_url` / `file_name` / `file_size`
- 接口 3.11 的 `download_record` 用 `resource_type` + `resource_id` 指向它
- 我在接口 v3.1 增补 15.1 的 scene 表里也写了 `resource` → `resource.file_url`

**但数据库设计 v3.0 里没有 `resource` 表**。3.9「其他模块（4张表）」只有
`view_history` / `download_record` / `ad_slot` / `app_config`。

建议补一张（字段按 3.11 的下载记录反推）：

```sql
CREATE TABLE `resource` (
```

## 九、给后端的确认清单

按「不确认就会出事」排序：

1. **`username` 怎么处理**：方案 A（可空 + 回填 `user_{id}`）还是方案 B（服务端生成）？
   这决定了客户端注册页要不要保留「用户名」输入框 —— 如果谁都拿不到它，UI 上就不该有。
2. **邮箱必须落 `email` 列，不能落 `phone` 列** —— `phone` 只有 `VARCHAR(20)`，
   常见邮箱（如 `zhangsan2026@university.edu.cn` = 31 字符）会被截断或直接报错。
3. **`uk_email` 必须加**，否则接口 1009「邮箱已被注册」无法实现。
4. **`phone` / `email` 不用时写 `NULL` 而非 `''`** —— 这条不遵守，唯一索引会误报「已注册」。
5. **`file_url` 返回永久直链还是签名 URL**：决定第四节那 9 个 `VARCHAR(255)` 要不要扩到 512。
6. **`file_record` 是否接受我这份 DDL**，特别是 `sha256` 去重与 `ref_count` 引用计数
   —— 如果后端不想做去重，可以直接删掉这两列，不影响接口契约。
7. **`resource` 表由谁补**：这是 v3.0 的既有缺口，与本次增补无关，但 12.1 下载接口依赖它。
8. **笔记 `source_id=0` 是否拒绝**：如果拒绝，我会把「新建笔记」入口从笔记本页挪到内容详情页。
